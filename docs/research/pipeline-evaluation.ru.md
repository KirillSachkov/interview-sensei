Агент (Codex): живая оценка #66, 2026-11-10.

# Что показала оценка

Все три агента извлекли шесть эталонных смыслов. Главная потеря происходит при устранении
повторов: вопрос из вакансии остаётся без ответа, хотя следующий материал содержит ответ.
Наполнение исправляет пустоту дополнительным веб-поиском, но расширяет критерии оценки.
На одинаковом ответе про Promise.all Claude Code и Codex поставили 3, OpenCode поставил 2.
Согласие моделей не заменяет проверку технических утверждений.

## Условия и воспроизведение

Основание: [#66](https://github.com/KirillSachkov/interview-sensei/issues/66),
[#14](https://github.com/KirillSachkov/interview-sensei/issues/14),
решения [#63](https://github.com/KirillSachkov/interview-sensei/issues/63),
влитые PR [#92](https://github.com/KirillSachkov/interview-sensei/pull/92),
[#95](https://github.com/KirillSachkov/interview-sensei/pull/95),
[#96](https://github.com/KirillSachkov/interview-sensei/pull/96),
[#98](https://github.com/KirillSachkov/interview-sensei/pull/98).
Начальная ревизия приложения: `5635915eb78978da4eb57f101a02e5d4a8f5c9fb`.

MacBook Pro, Node 24.21.0; Claude Code 2.1.316, Codex 0.167.0, OpenCode 2.2.6.
Адаптеры взяты из lockfile приложения. Модели и тарификация остаются выбранными пользователем;
это сравнение установленных агентов, а не изолированный эксперимент с одинаковой моделью.
В окружении нет ANTHROPIC_API_KEY и OPENAI_API_KEY. Подписка разрешена владельцем.
OpenCode использует свой настроенный provider; его стоимость не означает расход подписки Claude или Codex.

Приложение работало на loopback-портах 4446–4448 с тремя раздельными каталогами данных
под `/tmp/sensei-eval-66`. Для повторного Inbox после правки использовались 4450–4452
и ещё три временных каталога. Системные компоненты не устанавливались, распознавание видео
не запускалось. Изоляцию даёт штатный запуск приложения: Codex и OpenCode пишут в каталог данных;
Claude Code по ранее принятому исключению может писать собственное состояние в свой config.
Аудит всех записей файловой системы в этом опыте не проводился.

Прогоны запускались вручную агентом по поручению владельца через HTTP API приложения.
Сервер запускал настоящих агентов через ACP и давал им штатные MCP-инструменты и скиллы.
Это проверяет цепочку приложения, включая хранение, инструменты, отбор и запись оценок.
Браузер в живых прогонах не использовался; его пути проверяет отдельный e2e-набор с фейковым агентом.
Автоматическая оценка с расходом подписки в проект не добавлена.

1. Запустить сервер с новым `INTERVIEW_SENSEI_DATA_DIR` и свободным `SERVER_PORT`.
   Создать демо-цель через `POST /api/targets/demo`. Удалить её 30 встроенных вопросов
   через массовое удаление, выбрать агента через `PUT /api/targets/:id/agent`.
2. Загрузить четыре [учебных материала и эталон](pipeline-evaluation/expected.ru.md)
   в порядке vacancy, article, interview, operations через API загрузки файлов.
   Все материалы написаны для исследования; вакансия и транскрипт вымышлены.
3. Запустить `POST /api/targets/:id/inbox/processing`, дождаться отчёта, сохранить банк.
   Затем запустить `POST /api/targets/:id/answers/search` с `count: 10`.
   Очередь фактически содержит два пустых ответа, поэтому поиск обрабатывает два вопроса.
4. Провести три мока по шесть ответов в секции «TypeScript и Node.js» без лимита времени:
   неверные ответы, подготовленные сильные ответы, кнопка «Не знаю».
   После каждой оценки сервер просит следующий вопрос; перед завершением агент успевает
   показать седьмую карточку. Поэтому отдельно считаются показанные и оценённые вопросы.
5. Дополнительно проверить отбор по всем трём секциям и повторить оценку после правки скилла.
   Эти диагностические прогоны отделены от трёх основных моков.

## Извлечение и опорные ответы

| Метрика до правок | Claude Code | Codex | OpenCode |
| --- | --- | --- | --- |
| Покрытие эталонных смыслов | 6/6 | 6/6 | 6/6 |
| Добавлено вопросов | 6 | 6 | 8 |
| Вопросы опираются на материалы и соответствуют цели | 6/6 | 6/6 | 8/8 |
| Ответы из материала / без ответа | 4/2 | 4/2 | 6/2 |
| Время Inbox, секунд | 71,7 | 75,8 | 65,7 |
| Наполнено веб-поиском | 2/2 | 2/2 | 2/2 |
| Время наполнения, секунд | 50,5 | 64,6 | 51,5 |

У OpenCode два дополнительных вопроса сужают исходные: почему `as` не проверяет unknown
и откатывает ли отмена клиентского запроса серверную операцию. Первый существенно пересекается
с исходным Q1; второй выделяет отдельный аспект Q2. Это смысловое пересечение не видно счётчику
точных дубликатов сервера. Утверждать, что восемь вопросов лучше шести, оснований нет.

Все 14 опорных ответов из материалов содержат 3–5 пунктов и образец; при ручном сопоставлении
пункты соответствуют учебным материалам, технических противоречий эталону не найдено.
Это проверка небольших текстов на одну часть, без OCR и ошибок распознавания.

**Потеря ответа при повторе.** Q1 и Q2 сначала добавлены из вакансии без ответа.
Claude Code и Codex не прикрепили найденные далее ответы к существующим вопросам.
OpenCode создал близкие формулировки с ответами, оставив исходные вопросы пустыми.
Claude Code сам предупредил о потере в отчёте; Codex оставил `doubtful` пустым.
Серверный инструмент добавления не обновляет ответ существующего вопроса.
Объединение вынесено в [#100](https://github.com/KirillSachkov/interview-sensei/issues/100).

**Веб-поиск расширяет эталон.** Например, ответ Claude Code про AbortController получил
одноразовость сигнала, `AbortSignal.timeout`, `AbortSignal.any` и правила слушателей.
Подготовленный ответ из статьи этих деталей не содержит. В моке он получил 2 с раскрытием
2 из 5 пунктов. Получается, происхождение ответа влияет на требования к кандидату,
хотя сам вопрос сохранился.

**Есть неточные пункты даже со ссылками.** OpenCode описал `abort(reason)` как обязательный
`AbortError`, а для fetch/undici указал `ABORT_ERR`. На Node 24.21.0 отменённый fetch дал
`AbortError` с `code: 20` без аргумента и исходный `Error` без `code` с пользовательским reason.
Codex это различие сохранил; Claude Code отметил пользовательский reason в пункте ответа.
Это проверено локальным вызовом fetch с заранее отменённым сигналом, без сетевого запроса.
Правила reason подтверждают [Node.js](https://nodejs.org/api/globals.html#abortcontrollerabortreason)
и [Fetch Standard](https://fetch.spec.whatwg.org/#fetch-method).
По unknown ответы сопоставлены с [TypeScript Narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html)
и [описанием unknown](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-0.html).
Проверка соответствия каждого нового пункта источнику и калибровка вынесены в
[#101](https://github.com/KirillSachkov/interview-sensei/issues/101).

## Оценки и пределы сравнения

Во всех первых моках шесть заведомо неверных ответов получили Grade 0.
Сравнение сильных ответов ниже касается совпадающего смысла вопроса и одинакового текста
кандидата. Пункты опорного ответа агенты формулировали независимо, поэтому это измерение
стабильности всей цепочки, а не только оценщика на побайтно одинаковом эталоне.

| Подготовленный ответ до правки скилла | Claude Code | Codex | OpenCode |
| --- | --- | --- | --- |
| Promise.all, запуск операций до ожидания, отказ без отмены, пул, пример 100 fetch | 3 | 3 | 2 |
| Idempotency key, UNIQUE, атомарный результат, повтор и конфликт payload, внешний провайдер | 3 | 3 | 2 |

На двух общих вопросах попарное точное совпадение оценок составляет 2 из 6 сравнений (33%).
Максимальный разброс составляет один балл. Двух вопросов недостаточно для статистического
вывода о качестве модели. OpenCode отметил раскрытыми все пункты обоих ответов,
но снизил Grade за тезисность и дополнительные объяснения.

В первом сильном прогоне была ошибка сценария кандидата: сопоставление ответа про поток
искало слово `drain`, которого не было в формулировке вопроса про `write(false)`.
Поэтому все три агента получили вместо сильного ответа общую фразу про таймаут и нагрузку.
Оценки 0/1/1 на этом вопросе не считаются расхождением на сильном ответе.
Придуманные вопросы про outbox, различия unknown/any и восстановление платежа тоже
не относятся к исходному эталону и отдельно исключены из таблицы.
Исходные вопросы, опорные ответы, тексты ответов кандидата, оценки, времена и значения ACP сохранены в [данных исследования](pipeline-evaluation/results.json). Сырые журналы с адресами MCP и настройками не публикуются.

## Отбор и покрытие плана

В девяти основных моках показано 63 карточки и записано 54 оценки. Повторов одного
`questionId` внутри мока нет. Все агенты затронули три темы выбранной секции.
Максимальная серия одной темы в основных моках составляет три вопроса, углубления включены.
Отказ по превышению 3/4 вживую не провоцировался; его отдельно проверяют существующие тесты.

| Основные моки | Claude Code | Codex | OpenCode |
| --- | --- | --- | --- |
| Время: неверные / подготовленные / «Не знаю», секунд | 82,9 / 94,1 / 50,7 | 110,1 / 129,5 / 77,2 | 69,8 / 86,0 / 53,7 |
| Оценено неверных ответов с Grade 0 | 6/6 | 6/6 | 6/6 |
| «Не знаю» с Grade 0 от сервера | 6/6 | 6/6 | 6/6 |
| Повтор оценённых вопросов из первого мока во втором, среди 6 ответов | 5 | 4 | 5 |
| Вопросы с Grade 3 во втором, повторённые в третьем | 0/2 | 0/2 | неприменимо, Grade 3 не было |

**Отдых после Grade 2 можно обойти.** У OpenCode два questionId (unknown и медленный API)
повторились сразу после Grade 2. Кандидаты их не предлагали: агент нашёл вопросы через
`search_questions` и передал их напрямую в `present_question`. Код показа проверяет повтор
в текущем моке, но не отдых между моками. Вызовы и переданные id сохранены отдельно в [данных отбора](pipeline-evaluation/selection.json). Это существующий дефект исполнения правила;
тесты ранжирования сами по себе его не выявляют. Он зафиксирован в
[#103](https://github.com/KirillSachkov/interview-sensei/issues/103#issuecomment-6760202709).
Новые смысловые формулировки также получают новый id, поэтому отсутствие повтора id
не доказывает отсутствие смыслового повтора.

**Полный план.** В отдельном диагностическом моке каждому агенту даны все три секции
и 12 ответов «Не знаю»; показана ещё одна неотвеченная карточка перед завершением.
В первой дюжине распределение «опыт / темы / проектирование» составило 2/9/1 у Claude Code,
4/6/2 у Codex и 3/7/2 у OpenCode. Время составило 92,4 / 162,1 / 102,6 секунды соответственно.
Все три секции покрыты. Claude Code вернулся из проектирования к темам до следующего круга;
OpenCode прошёл секции по порядку, затем начал следующий круг. Отступления от долей
и порядок переходов зависят от агента, хотя сервер рассчитывает подсказку.
В [#103](https://github.com/KirillSachkov/interview-sensei/issues/103) отдельно вынесено решение,
насколько жёстко сервер должен закреплять план. Изменять веса ради этого наблюдения оснований нет.

## Простые улучшения

В `sensei-inbox` добавлено правило сохранять существующий вопрос и отмечать в сомнениях
материал и часть, откуда нельзя прикрепить найденный ответ. После правки все три агента
отметили Q1 и Q2 с правильной частью; Codex до правки не отметил ни одного.
Это делает потерю видимой, но не восстанавливает ответ. Повтор был проведён на свежих данных
с теми же четырьмя материалами. Claude Code и OpenCode предлагают ручное добавление;
кандидат может исправить ответ через чат настройки.

В `sensei-interview` уточнено применение существующей шкалы: краткий ответ может получить 3,
а снижение оценки должно называть конкретный пробел по вопросу и критериям секции.
Дополнительные полезные детали сами по себе не становятся обязательными.
Веса отбора не менялись: данных недостаточно, чтобы доказать пользу других весов.
Тестов, которые лишь ищут фразы в скилле, не добавлено; изменение проверяется живыми прогонами.

В повторе оценки на исходных вопросах после правки OpenCode поставил 3 за Promise.all
и 3 за идемпотентность, раскрыв все пункты; раньше было 2 и 2 на тех же текстах ответов.
Claude Code и Codex снова поставили 3 за идемпотентность, но затем выбрали новые вопросы-углубления,
поэтому их вторые ответы не включаются в сравнение исходных вопросов.
Промежуточный диагностический прогон также показал 3 вместо 2 у OpenCode на ответе
про медленный API. Это наблюдаемое улучшение одного повтора, а не доказательство устойчивости.

В скилле также явно разделены результаты `search_questions` и допустимые кандидаты
текущего хода: показывать готовый bank questionId можно только из ответа отбора.
В повторе OpenCode при двух оставленных в банке отдыхающих вопросах после Grade 3
не показал ни один из них: четыре ответа и пятая неотвеченная карточка относились
к новым вопросам. Это проверяет следование скиллу в одном опыте; серверный обход
по-прежнему возможен и остаётся в #103.

## Ограничения

Это один запуск на агент для каждого сценария, на собственной короткой учебной подборке.
Он не заменяет проверку владельцем на его материалах, длинных источниках, дизайне системы,
живом общении и транскриптах с ошибками. Время включает запуск агента и ожидание; параллельные
прогоны и проверки проекта делят ресурсы машины. Это не сравнительный бенчмарк скорости моделей.
Результаты недетерминированы и не доказывают качество каждого будущего запуска.

Точный расход оплаченных токенов через текущий ACP недоступен: `used` показывает текущий
контекст, стоимость сообщает не каждый агент. Сумма `used` по ходам не является расходом.
Исследование отдельной метрики вынесено в [#102](https://github.com/KirillSachkov/interview-sensei/issues/102).
